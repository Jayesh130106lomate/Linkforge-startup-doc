# Standard Operating Procedure: Incident Management & Disaster Recovery

---

**Document status:** incident-response and recovery procedure. Severity, response times, health checks, failover behaviour, backup capability, and customer communication paths must be validated through drills, monitoring, and postmortems.  
**Last reviewed:** 21 October 2026

## 1. Overview & Operational Objectives

LinkForge is designed for campaign links and dynamic QR codes, so redirect or dashboard disruption can affect customer campaigns and reporting. The actual traffic and financial impact of an incident must be assessed from current telemetry and customer reports; this document does not assume a spend volume.

This Standard Operating Procedure (SOP) defines how the LinkForge engineering and operations team classifies system anomalies, executes rapid diagnostic triage, engages architectural failover mechanisms, and conducts blameless post-mortems.

## 2. Incident Severity Classification & Response Targets

| Severity Level | Definition | Impact Examples | Response target | Leadership engagement |
| :--- | :--- | :--- | :--- | :--- |
| **SEV-1 (Critical)** | Core redirect engine failure or widespread data loss | • Cloudflare Worker edge redirects failing globally<br>• Primary PostgreSQL database unreachable<br>• Zero link resolutions across all domains | **Immediate (<15 mins)**<br>*24/7 on-call* | Founder & Lead Engineer (Jayesh Lomate) |
| **SEV-2 (Major)** | Platform application or core pipeline degraded | • Dashboard (`app.linkforge.site`) login unavailable<br>• Link creation / QR styling failing<br>• BullMQ click ingestion worker queue stalled<br>• Dodo Payments webhook delivery failure | **< 30 minutes** | Lead Engineer & Core Team |
| **SEV-3 (Minor)** | Non-critical feature impairment with available workaround | • Analytics chart rendering delay<br>• CSV export queue running slowly<br>• Isolated non-blocking UI discrepancy | **< 4 hours** | Technical Support & Operations |
| **SEV-4 (Low)** | Minor bug or cosmetic defect | • Typo in user interface copy<br>• Non-standard browser layout quirk | **Next Release** | Assigned during regular sprint cycle |

## 3. Diagnostic Procedures & Real-Time Health Probes

When a system anomaly is detected or reported:

### 3.1 Operations Dashboard Inspection
Navigate immediately to the administrative operations console:
* **Reported route**: `https://app.linkforge.site/admin/operations` (confirm access controls and current availability in production).
* **Verify Key Gauges**:
  1. **Production Readiness Score**: Live composite score generated by `productionReadiness()` (`src/lib/readiness.ts`).
  2. **Worker Queue Status**: BullMQ active, delayed, waiting, and failed job counts.
  3. **Failed Webhooks**: Inbound Dodo Payments webhooks requiring manual retry.
  4. **Analytics Retention**: Table partition boundaries and row expiration readiness.

### 3.2 Automated System Diagnostic Commands
From the production deployment environment or staging replica:
```bash
# 1. Run full release readiness and schema validation suite
npm run release:check

# 2. Check and maintain PostgreSQL analytics table partitions
npm run partitions:maintain

# 3. Verify Prisma database schema synchronization
npm run db:deploy
```

## 4. Failover Protocols & Degraded-Mode Resilience

LinkForge's architecture was engineered specifically to prevent single-point-of-failure outages:

```
[ Incoming Visitor Click on Branded Short URL ]
                       │
                       ▼
         [ Cloudflare Worker Edge Tier ]
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
    [ Layer 1: Cache ]  [ Cache Missing / Redis Down ]
      (Redis Hit: <15ms)         │
                                 ▼
                     [ Layer 2: PostgreSQL Origin ]
                       (Direct Indexed Query: <45ms)
                                 │
                                 ▼
                 [ Redirect target: low latency ]
```

### 4.1 Redis Outage or Cold Restart SOP
* **Resilience Principle**: Redis is strictly an accelerator and queue broker; **PostgreSQL is the permanent source of truth**.
* **Automatic Degraded Mode**: If Redis becomes unreachable or suffers total memory eviction:
  1. The Cloudflare Worker edge and origin API gracefully catch the connection timeout.
  2. The system falls back automatically to direct PostgreSQL indexed queries (`shortCode`, `domainId`).
  3. Visitor redirects continue without interruption, maintaining sub-100ms response times.
* **Recovery Action**:
  - Re-provision or restart the Redis instance.
  - The cache will self-heal naturally as incoming clicks repopulate hot keys. Do not run mass cache warmers that cause origin database stampedes.

### 4.2 BullMQ Click Ingestion Queue Backlog SOP
* **Condition**: High-volume ad bursts result in queued click events exceeding worker processing throughput.
* **Triage Action**:
  1. In `/admin/operations`, inspect the failed jobs queue.
  2. Scale worker concurrency (`src/lib/queue/worker.ts`) or spin up a dedicated worker replica.
  3. Verify whether redirect execution is isolated from click tracking in the affected deployment. This is a design expectation that requires a failure-path test.

### 4.3 Database Incident & Snapshot Restoration Runbook
* **Condition**: Severe database hardware failure or data corruption.
* **Recovery Procedure**:
  1. Initiate Point-in-Time Recovery (PITR) to the last verified consistent state via the managed PostgreSQL console.
  2. Provision a new isolated target database instance.
  3. Verify schema baseline integrity: `npm run db:deploy`.
  4. Rebuild PostgreSQL GIN trigram indexes (`*_trgm_idx`) and run `npm run partitions:maintain`.
  5. Point application environment variable `DATABASE_URL` to the restored instance and trigger deployment reload.

## 5. Incident Communication & Status Updates

During active SEV-1 or SEV-2 incidents, maintaining transparent customer communication is critical:

1. **Initial Acknowledgment (Within 15 mins for SEV-1)**:
   - Post an initial status advisory on public channels:
     > *"We are currently investigating an issue affecting dashboard access and link creation. Edge link redirects remain operational. Our engineering team is actively resolving the matter."*
2. **Periodic Updates**: Post verified progress updates every **30 minutes** until resolution.
3. **Resolution Confirmation**: Notify affected agencies directly once telemetry confirms sustained nominal latency for at least 15 consecutive minutes.

Do not state that redirects remain operational, a root cause, an ETA, or a customer-data impact until it is verified. If scope is uncertain, say what is being investigated and when the next update will be provided.

## 6. Blameless Post-Mortem Standard Operating Procedure

Within 48 hours of any SEV-1 or SEV-2 incident resolution, the engineering lead must publish an internal Post-Mortem report using the following standard template:

### Post-Mortem Report Structure
1. **Incident Summary**: Date, duration, affected components, and business impact.
2. **Timeline of Events (IST / UTC)**:
   - T0: Incident onset.
   - T1: Detection / alert received.
   - T2: Engineering triage initiated.
   - T3: Mitigation applied.
   - T4: Full recovery verified.
3. **Root Cause Analysis (5-Whys)**: Identifying the fundamental underlying architectural failure rather than assigning human blame.
4. **What Went Well**: Rapid detection, automated graceful fallback, or efficient communication.
5. **Where We Got Lucky**: Mitigating factors that prevented wider customer exposure.
6. **Action Items & Preventative Engineering**: Specific GitHub issues created with assignees and due dates to eliminate the failure mode permanently.

## 7. Incident Roles and Evidence

Assign the following roles for every SEV-1 or SEV-2 incident; one person may fill multiple roles in a small team, but the assignments must be recorded.

| Role | Responsibility |
| :--- | :--- |
| Incident commander | Declares severity, coordinates work, maintains the timeline, and owns the decision to resolve. |
| Technical lead | Diagnoses and applies/reviews mitigation with a rollback plan. |
| Customer communicator | Publishes confirmed updates and maintains the affected-customer list. |
| Scribe | Records commands, decisions, timestamps, evidence links, and follow-up actions. |

For every incident retain: alert source, severity decision, impact/scope, timeline in UTC and IST, key metrics/screenshots/exports, changes made, rollback decision, customer communications, root cause or current hypothesis, data-loss assessment, and follow-up owner/date. Run at least one tabletop exercise and one restoration exercise annually, then update this SOP with the lessons learned.
